# 故障排查与安全模式 (Troubleshooting & Safe Mode)

本指南提供 Bitty 的排错诊断流程、自检命令以及恢复策略。

## 应急安全模式 (`--safe`)

如果新安装的插件、配置文件语法错误或不兼容的硬件状态导致 Bitty 无法正常启动，请以**安全模式 (Safe Mode)** 启动：

```bash
bitty --safe
```

### 安全模式的行为特点

- **禁用所有插件**：完全忽略所有第三方插件，不实例化任何 Lua 虚拟机。
- **强制使用内置默认值**：绕过用户的 `init.lua`，Bitty 直接采用编译内置的兜底默认配置启动。
- **挂起文件监听**：临时停用动态文件监听器与后台重新加载钩子。

安全模式允许你正常打开终端会话，定位出错的配置文件或移除损坏的插件，避免 GUI 冲突闪退。

安全模式下的 CLI 动词（`bitty doctor`、`bitty config check`、`bitty plugin list`）无需任何插件 VM 即可运行，因此即使插件本身就是问题所在，诊断依然可用。无头 parity 套件锁定了这一点：安全模式是完整的启动姿态，而非降级猜测。

## 插件激活错误（含义对照）

宿主在激活前校验每个插件并失败关闭——被拒绝的插件只会被禁用并给出诊断，绝不会部分激活。对照下表定位你看到的现象：

| 现象                                      | 含义                                                                                                                                                                            | 修复                                                                                                     |
| :---------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------- |
| 安装退出码 `4` 并给出 compat 诊断         | 插件 `[compat] bitty` 范围与你的宿主无交集（例如插件下限高于你的版本，或你的版本高于其上限）。官方插件下限为 `>=0.0.21,<0.1`，覆盖整个 0.0.x 系列；被拒绝意味着真正的版本错位。 | 升级 Bitty，或安装范围覆盖你宿主的插件版本。上限故意收紧，因为 0.x 小版本可能 breaking。                 |
| 更新后 `bitty plugin list` 显示插件被禁用 | 加载时记录版本或 capability 不匹配（`disabled_reason`）；插件未注册任何东西——没有命令、没有 keymap、没有 overlay。                                                              | 同上；升级后用 `bitty plugin enable <id>` 重试。                                                         |
| 状态栏在渲染，但某个模块缺席              | 不是错误：provider 缺席、未授权、过期、被撤销或格式错误，模块失败关闭隐藏。Provider 只发原始数值——数据源丢失退化为缺席，绝不归零。                                              | 授权 capability（`bitty plugin list` 显示已授与与申请项），或在无此硬件的宿主上接受隐藏。                |
| 点击状态栏控件只弹出通知而不执行          | 缺少控制授权或宿主拒绝调用（`E_NOT_PERMITTED`）。点击按设计降级为通知——绝不重试或提权。                                                                                         | 在安装/同意时授予控制 capability，或保持只读渲染。                                                       |
| 激活时出现 `E_SETTINGS_UNDECLARED`        | 插件作者 bug：插件读取了从未声明的 settings 键。用户无法从配置文件修复。                                                                                                        | 向插件上报；期间用 `bitty --safe` 继续工作。                                                             |
| 插件配置文件的值看似被忽略                | 可能该键未知（被记录为跳过，不改变任何东西）、类型错误（该键回退到默认值）、整个文件失败关闭（重复键或结构垃圾——全部按默认值运行），或该值需要你未批准的授权。                  | 运行 `bitty config check`，逐键对照插件声明的 settings，并用 `bitty plugin list` 检查已授与 capability。 |

> [!NOTE]
> **PENDING —— 真机激活证明。**各扩展在真实宿主上的逐个真机激活正在 0.0.23 验证战役中取证。无头安装正常但真机行为异常的插件属于验证级上报：请附 `bitty doctor --format json` 输出及插件 id 与版本。

## 兼容下限

两道下限决定什么能跑在哪里，且都以诊断失败关闭而非崩溃：

- **插件到宿主下限**：每个 manifest 声明 `[compat] bitty`（官方插件：`>=0.0.21,<0.1`）与 `plugin-api = "^1.0"`。宿主在安装时求交集；无交集则不激活，退出码 `4`。
- **软件包到发行版下限**：原生 Linux 包按格式声明运行时依赖（fontconfig、freetype、libgcc 系列），且每个包在发布前都在其发行版的干净容器中做安装冒烟测试。无关发行版仅为 best-effort，不算支持——请改用安装脚本或从源码构建。

## 离线校验配置文件

在重新加载终端前，可以在不启动图形界面的情况下离线验证 Lua 配置文件：

```bash
bitty config check
```

- 若所有语法与 Schema 字段均合法，返回退出码 `0`。
- 若解析或校验失败，输出具体的行号、列偏移量与错误描述。

## 插件诊断自检 (`bitty plugin list` + `bitty doctor`)

当插件行为异常、运行迟缓或丢失事件时，检查其记录与宿主环境：

```bash
# 已记录插件、来源、状态与能力授予
bitty plugin list

# 单个插件的清单与已记录授予
bitty plugin info <id>

# 宿主环境健康度（GPU、字体、依赖）
bitty doctor
```

> [!NOTE]
> 不存在 `bitty plugin doctor` 动词。Live 的单 VM 内存、燃料与队列丢弃自省尚未暴露到 CLI。

## 扩展与工具派生故障

该领域的故障按设计失败并关闭：不会留下半安装状态，也不会执行或打印任何不可信内容。

- **`bitty extension install` 锁定不匹配（退出码 `4`）**：拉取版本的摘要与记录的 TOFU 锁定不一致。锁定永不自动更新，请带外核验版本无误后，以 `--force` 显式重新锁定。
- **`show-source` 无输出（退出码 `4`）**：安装缺失，或可执行文件已不再匹配其锁定的描述符哈希。请重新安装该扩展；Bitty 拒绝打印不可信字节。
- **工具派生被约束拒绝**：在 Linux 上，已放行的工具派生运行在 Landlock 可执行约束之下；命名约束的拒绝意味着约束建立失败（如 5.13 以前的内核，或容器策略禁止非特权约束），该次派生已被拒绝而非无约束运行。在 macOS 与 Windows 上，已放行的工具派生在平台机制落地前均失败并关闭，并给出约束诊断。
- **更新后能力被拒绝**：授权绑定到精确的清单哈希。请重新运行 `bitty plugin install` 并批准新的确认提示；以 `bitty plugin revoke <id> --cap <capability>` 可撤销单个授权而不移除插件。

## 日志文件与详细程度

Bitty 依据操作系统规范将结构化诊断日志写入磁盘：

- **Linux / BSD**：`$XDG_STATE_HOME/bitty/bitty.log`（默认为 `~/.local/state/bitty/bitty.log`）
- **macOS**：`~/Library/Logs/bitty/bitty.log`

### 提高日志详细程度

从现有 Shell 启动时设置 `RUST_LOG` 环境变量：

```bash
RUST_LOG=bitty=debug,bitty_runtime=trace bitty
```

## GPU 与渲染后备方案 (GPU Fallbacks)

Bitty 基于 `wgpu` 自动选择可用的最快原生图形后端（Linux 下为 Vulkan，macOS 下为 Metal）。

如果你的环境缺乏硬件 GPU 加速（例如在虚拟机或纯软件渲染的容器内）：

```bash
# 强制回退至 OpenGL 后端
WGPU_BACKEND=gl bitty

# 强制选择低功耗 GPU 适配器
WGPU_POWER_PREF=low bitty
```
